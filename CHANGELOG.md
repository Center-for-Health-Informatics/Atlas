- **[atlas] Data Sources histograms and boxplots rendered with bars/whiskers clipped at a uniform height, even though tooltips showed the correct, varying values.** Root cause: `atlascharts`' shared chart renderers compute their y-axis (or x-axis, for the horizontal boxplot) domain with `d3.max(data, d => d.someField)`, and `d3.max` compares with plain `<` — so if `someField` is a string (as `COUNT_VALUE` and friends arrive from WebAPI JSON, uncoerced), the comparison is **lexicographic**, not numeric: `"11" < "8"` is `true`, so `d3.max` locks onto `"8"` as the max even when `11` is the real one. Verified directly: `node -e "console.log(require('d3-array').max(['3','8','11','5'], d=>d))"` prints `8`. The resulting too-small domain pushes any bar whose true value exceeds it to a negative `y()`/`x()`, taller/wider than the container, and the SVG clips everything past the plot origin — while the d3-tip tooltip, built straight from the same raw (uncoerced) value, correctly shows the real number, producing the "bars pinned at one height but tooltip disagrees" symptom. This is not a rare edge case: it triggers whenever a dataset's true max count crosses a digit-count boundary (single- vs double-digit, 99 vs 100, etc.), which is routine for real person-count distributions — hence it hit Year of Birth, Age at First Observation, Observation Period Length, and Continuous Observation by Year alike, all of which share this code path. Fixed at two layers: (1) the shared renderers in `js/vendor/atlascharts/{histogram,barchart,boxplot,horizontal-boxplot}.js` now coerce with `+` at every `d3.max`/`d3.min` domain call (and `Histogram.mapHistogram` coerces `COUNT_VALUE` at the source), which protects every caller regardless of whether the caller remembers to numify its data; (2) the three Data Sources report call sites (`js/pages/data-sources/components/reports/{person,dashboard,observation-period}.js`) now pass `numerify: true` to the existing `ChartUtils.normalizeArray()` helper, so the data is numeric from the point it's read out of the API response rather than relying on the renderer to paper over stringly-typed input. Individual bar/whisker *positions* (`y(d.q1)`, `x(d.max)`, etc.) were not at risk from this same bug — d3-scale's linear scale function does numeric subtraction internally, which auto-coerces strings, unlike `d3.max`'s strict `<`. Note: this fork also has a separate, unbuilt checkout of the upstream `OHDSI/Visualizations` repo at a sibling path outside `atlas/` (since removed) — it was not wired into the Vite build (the `atlascharts` bare import resolves via a `vite.config.js` alias to the in-repo `js/vendor/atlascharts/`), so an initial fix applied there had no effect until it was reapplied to the real vendored copy. Verified: `npm run lint` clean, `npm test` 85/85, and `d3-array`'s `max()` behavior confirmed directly (string comparison returns `8`, numeric returns `11`). Live browser verification against real Achilles data is still pending — the dev-accessible WebAPI test instance wasn't reachable from the environment this fix was made in.

- **[atlas] The production bundle had not booted at all since the Vite 5.4 → 8.1 upgrade; reverted to Vite 7.3.6.** Symptoms in the browser console were `TypeError: d is not a function` (minified `class extends d(i)`, i.e. `class DropDownMenu extends AutoBind(Component)`), then `Class extends value undefined is not a constructor` in the chart hierarchy, then `Cannot destructure property 'ViewMode' of 'c' as it is undefined` — each one surfacing only after the previous was worked around. Root cause: Vite 8 replaces Rollup with **Rolldown**, and Rolldown's code splitting emits a *cyclic chunk graph* for this codebase. Across a chunk cycle a `const`/`class` binding gets read before the defining chunk has executed, so imported base classes and mixins are `undefined` at class-definition time. Measured rather than guessed: Tarjan over the real Vite module graph (2069 modules, real aliases) finds no relevant *source* cycle — one first-party SCC, `cohortbuilder/CriteriaTypes`, plus d3's own benign ones, with `AutoBind.js` and `Chart.js` in none — while Rolldown's emitted *chunk* graph contains one 5-chunk cycle, `conceptset-list ↔ ComparativeDistributionStatConverter ↔ const ↔ components ↔ Router`, present with and without any `manualChunks`. The same source built with Vite 7 / Rollup yields **zero** chunk cycles and boots clean. Rollup guarantees an acyclic chunk graph by assigning modules per entry-point signature; Rolldown does not, here. Corroborated upstream by [vitejs/vite#21866](https://github.com/vitejs/vite/issues/21866) (maintainer-labeled `bug: upstream`) and [rolldown-vite#597](https://github.com/vitejs/rolldown-vite/issues/597) ("circular chunk dependency causes TDZ error"). Downgraded `vite` to `^7.3.6` and `@vitejs/plugin-legacy` to `^7.2.1` (8.x requires Vite 8), and **removed** the two workarounds written against the bug — `AutoBind` had been converted to a hoisted function declaration to dodge the TDZ, and `vite.config.js` carried a `charts` `manualChunks` group to co-locate the chart hierarchy; neither is needed under Rollup and neither should come back. Also fixed a stale `allowScripts` entry in `package.json` (an earlier `npm pkg set` had written a junk `"esbuild@0"` key, since dots are path separators there) and replaced `esbuild@0.21.5` with the now-current `esbuild@0.28.1`. Two false starts worth recording so they aren't repeated: an early cycle check that reported "zero cycles" was meaningless because it listened for Rollup's `CIRCULAR_DEPENDENCY` warning code, which Rolldown never emits; and a grep of the emitted chunks for `from"./..."` missed the Router→conceptset-list edge entirely, because bare side-effect imports (`import"./x.js"`) have no `from`. Verified: `npm run lint` clean, `npm test` 85/85, 0 chunk cycles, and a production **container** driven headless renders the full app with zero JavaScript errors (WebAPI CORS/TLS errors against a `localhost` origin are expected and are not app faults — in real deployment Atlas and WebAPI are same-origin behind nginx).
