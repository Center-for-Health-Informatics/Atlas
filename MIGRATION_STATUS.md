**Production build: fixed as of 2026-07-08 — but that only covered `vite build` itself, not the Docker deployment path.** `build:dev` now runs `vite build --config vite.config.js` directly; `build` and `build:docker` compose on top of it unchanged. `build/optimize.js` (the old RequireJS optimizer + Babel + Terser path) and `build/polyfill.js` (only used by it, superseded by `@vitejs/plugin-legacy`) are deleted.   - **Correction, 2026-07-10:** `vite build`/`vite preview` working was never the same claim as "the Docker image serves working production output" — and it didn't. `Dockerfile` had never actually been run end-to-end since before the migration (missing `COPY ./vite.config.js`, wrong `index.html` copy order — both fixed 2026-07-10) and, once it *did* build, its final stage was copying the raw source tree into the served image instead of Vite's real `js/assets/bundle/` output — meaning every Docker-deployed Atlas was shipping unexecutable raw ESM source, not the bundle `vite preview` had verified. Also found and fixed a genuine production-only app bug that `vite preview`'s smoke-check apparently never exercised deeply enough to catch: a `ko.i18n` registration-order bug in `js/const.js` that only breaks under Rollup's production chunking (dev server is unaffected). See `CHANGELOG.md` (2026-07-10) for full details on all of this. Lesson for future verification: "the build succeeds" and "the bundle loads via `vite preview`" are necessary but not sufficient checks — verify the *actual deployment artifact* (the Docker image, run the way it's really run) in a real browser before calling production done.
  - This also exposed and fixed a latent bug in `genversion`: the old `genversion -s js/version/version.js && r_js -convert js/version js/` pipeline produced an AMD `define()`-wrapped `js/version.js`, which the ESM app can't import (`"version" is not exported by "js/version.js"`) — this had been masked until now because `build/optimize.js` silently no-op'd before anything tried to actually load the bundle. Replaced with a single step: `genversion -e -s js/version.js`, which writes plain ESM (`export const version = ...`) directly — no intermediate directory, no `r_js -convert`, no `rimraf` needed.
  - **Pinned to Vite 7, deliberately, 2026-07-30.** The repo briefly ran Vite 8.1.5, which replaces Rollup with **Rolldown**. Rolldown's code splitting emits a *cyclic chunk graph* for this codebase, and across a chunk cycle a `const`/`class` binding is read before the defining chunk has executed — so imported base classes and mixins are `undefined` at class-definition time (`d is not a function`, `Class extends value undefined is not a constructor`, `Cannot destructure property 'ViewMode' of 'c'`). The production bundle simply did not boot; the dev server was unaffected, which is why it went unnoticed from the 5.4 → 8.1 upgrade (week of 2026-07-20) until 2026-07-30.
    - Measured, not guessed. Source module graph: no relevant cycle — Tarjan over the real Vite graph (2069 modules, real aliases) finds one first-party SCC, `cohortbuilder/CriteriaTypes`, plus d3's own benign ones; `AutoBind.js` and `Chart.js` are in none. Emitted chunk graph under Rolldown: **one 5-chunk cycle**, `conceptset-list ↔ ComparativeDistributionStatConverter ↔ const ↔ components ↔ Router`, present with and without any `manualChunks`. Same source under **Vite 7 / Rollup: zero chunk cycles**, boots clean. Rollup guarantees an acyclic chunk graph by assigning modules per entry-point signature; Rolldown does not, here. Compare upstream [vitejs/vite#21866](https://github.com/vitejs/vite/issues/21866) (labeled `bug: upstream`) and [rolldown-vite#597](https://github.com/vitejs/rolldown-vite/issues/597).
    - Security posture was checked before downgrading: `vite@7.3` is a supported branch receiving **important fixes + security patches** (see <https://vite.dev/releases>), and no advisory is patched in 8.x while left open in 7.x — the two lines are patched the same day. `npm audit` is identical on both trees.
    - Two workarounds written against the Rolldown bug (a hoisted-function `AutoBind`, and a `charts` `manualChunks` group) were **removed** on the downgrade; neither is needed under Rollup. Don't reintroduce them. Revisit Vite 8 only after re-measuring the emitted chunk graph for cycles.
    - **`INEFFECTIVE_DYNAMIC_IMPORT`: fixed 2026-07-30.** Four modules were both statically and dynamically imported — `conceptset/ConceptSetStore.js`, `conceptset/concept-modal.js`, `conceptset/conceptset-editor.js`, `entityBrowsers/cohort-definition-browser.js` — which entangles those chunks under any bundler. The dynamic side was always the redundant one: 20 dynamic imports across `cohort-definitions/routes.js`, `concept-sets/routes.js` and `profiles/routes.js`, of which 19 discarded the resolved value entirely. Three of the four modules are bare side-effect imports that register a Knockout component at module scope, and the convention everywhere else in `js/components` is that a parent component statically imports its children (`conceptset-list` → `expression` → `conceptset-editor`; `included` → `concept-modal`) — so the route-level copies bought nothing. Two `cohort-definition-browser` dynamic imports *were* load-bearing (`cohort-definitions.html` and `report-manager.html` use the tag but their JS did not import it) and became static imports in those two component modules; two others (`concept-sets`, `profiles`) referenced a tag those pages never render at all. The one real value import, `ConceptSetStore` at the conceptsets route, existed only to prime `sharedState.activeConceptSet`; that now happens in `cohort-definition-manager`'s `loadConceptSet`, the single funnel for a route-supplied `conceptSetId`, which already holds the same store singleton. The same file's 8-item `Promise.all` array, copy-pasted across five routes, was hoisted into one `loadCohortEditor()` helper — that copy-paste drift is what produced the warnings in the first place.
      - Removing the dynamic imports did **not**, on its own, move any of the four out of the eager `Router` chunk (1,053,936 → 1,049,012 bytes, −4.9 KB). The cause was a *different* outlier, fixed immediately after — see the next bullet.
    - **`characterizations/routes.js` de-eagered, 2026-07-30.** It was the only `routes.js` in the repo with a **static** component import (`import './components/characterizations/characterization-view-edit'`), needed because its two `characterizationViewEdit` routes and its `version` route called `setCurrentView` synchronously. That single edge dragged the whole characterizations component tree — and through `characterization-conceptsets` → `conceptset-list` and `characterization-design` → `linked-cohort-list`, all four of the modules above plus JSZip — into the boot-critical chunk. Those three routes now load the component dynamically like every other page. Result: `Router` chunk **1,049,012 → 59,292 bytes (−94%)**, its static edge to `jszip.min` (97 KB) gone, all four modules split into their own lazy chunks, 96 → 150 chunks, and still **zero chunk cycles**. The honest end-to-end number is smaller than the chunk number, because the freed content partly redistributes into other chunks the boot still pulls: JS actually transferred to render `#/home` in a real browser went **1,609,197 → 1,432,229 bytes (−177 KB, −11%)**, across 31 → 40 requests. Quote the −11%, not the −94%.
      - **This unmasked three latent missing registrations, and that is the lesson.** With the characterizations tree no longer eager, `#/conceptset/:id/conceptset-expression` threw `Unknown component` for `warnings`, `warnings-badge` and `conceptset-list-included-badge`: `concept-sets/conceptset-manager.js` names those components (`componentName: 'warnings'`, and `hasBadge: true` tabs, which `components/tabs.html` renders as `${componentName}-badge`) but never imported the modules that register them — it had been riding on the eager characterizations tree. Fixed by importing them where they are used, per the usual convention: `components/checks/warnings` (which pulls in `./warnings-badge` itself) and `components/conceptset/included-badge`. Found by sweeping all 28 routes in a browser on both builds and diffing the error sets — nothing static would have caught it, and neither would the dev server. **Expect more of these** any time a page stops being eagerly loaded: a component that names another component by string but does not import it is invisible until the accidental eager path disappears.
      - **The remaining 20 of these were then found statically and fixed, 2026-07-30, and the check is now committed as `npm run check:registrations` (`build/check-registrations.mjs`).** The checker resolves every `js/pages/*/routes.js` route to the set of modules it actually loads (its dynamic imports' static closures, plus the routes.js file's own closure, minus everything reachable at boot), collects the component names that set of modules references — element tags in the paired `.html`, `componentName:` / `component: { name: }` strings, and the implicit `${componentName}-badge` for `hasBadge` tabs — and reports any whose registering module is not in the set. It reads the aliases out of `vite.config.js` directly rather than keeping a second copy, because a stale alias table silently truncates closures and invents failures. Zero false positives in practice: every unresolved specifier it drops is a real npm package or a `?raw` HTML import, none of which register components. It found 35 gaps across 16 modules — mostly `access-denied`, `faceted-datatable`, `heading-title`, `concept-set-browser`, `initial-criteria-editor`/`criteria-group` and `analysis-execution-list` — each fixed with a bare import in the module whose own template uses the tag. **None of these had ever shown up in a browser sweep**, because they all sit behind a condition a smoke test does not reach: `<access-denied>` renders only for a user without permission, and the rest live inside modals and inactive tabs. Boot payload after all 20 imports: 1,432,167 bytes, i.e. unchanged — they all land in lazy chunks. One knock-on: `cohort-definition-manager.html` binds `<report-manager>`, so `cohort-definition-manager.js` now imports it statically and the corresponding dynamic imports had to come out of `loadCohortEditor()` and the `/reports` route, or `INEFFECTIVE_DYNAMIC_IMPORT` would have come straight back.
      - **Two long-standing runtime errors fixed at the same time**, both pre-existing and both invisible to the type/lint/test layer. (1) `/reports` — the standalone route renders `report-manager` with *no params at all*, but the constructor assumed every param was an observable owned by `cohort-definition-manager`, so `reportValid` called `undefined` and the route died on bind; the params now fall back to their own observables. Its selection area (the `showSelectionArea` block, rendered only on this route) also read `$root.reports()` and `$root.hasResults`, neither of which exists anywhere in the codebase, and `$component.sharedState`, which was never assigned — all three now live on the component, with the report list derived from `cohortReportingService.visualizationPacks` (the same source of truth `runReport` switches on). (2) `ReferenceError: personId is not defined` on the cohort definition editor — `explore-cohort.html` used XHTML-style self-closing `<div … />` and `<a … />`, which HTML does not honour; the unclosed `<div data-bind="text:…" />` reparented the `foreach` blocks below it and the anchor bound outside its `foreach` context. Closing the tags properly fixes it.

Page/console error sets are byte-identical to a pre-change control build. Final state: all 28 routes swept in headless Chromium against a real WebAPI — **zero page errors, zero `Unknown component`**, down from the two residual errors above.
      - **The convention itself is now enforced, not just the breakage, 2026-07-30.** The per-route check above answers "is anything broken today"; it does not answer "does each module import what its own template uses". A second pass over every `.js` with a paired `.html` found **47 references across 35 modules** in the weaker state — the module's own template names a component its own import closure never reaches, so it works only because a sibling on the same route happens to have loaded the registration. None were live bugs, but every live bug this checker has found started here. Fixed with **42 bare imports** (47 → 42 because some collapse: importing the `cohortbuilder/components` barrel covers `criteria-group`, `demographic-criteria` and `windowed-criteria` at once). Cost: boot payload **1,432,167 → 1,432,225 bytes, +58**, and `Router` 58,819 → 59,023 — they all land in lazy chunks, as expected. `check-registrations.mjs` now runs both passes and exits 1 on either.
        - The one thing worth watching: three of these imports (`WindowedCriteria`, `CensoringCriteriaEditor`, `InitialCriteriaEditor` → the `cohortbuilder/components` barrel and `from-reusables-modal`) join an import cycle that already existed, growing that source-level SCC from 4 modules to 7.         - Known limitation, documented in `CLAUDE.md`: the checker models import **closure**, not direct imports, so it cannot flag removing an import whose registration some *other* dependency also pulls in. 45 references are in that doubly-covered state. A naive "must import the registering file directly" rule reports 28, but nearly all are false positives — barrel modules (`cyclops`, `iranalysis/main`) that are directly imported while the registration lives one file deeper. Closure is the rule that can be soundly enforced; the direct import is still the one to write.
